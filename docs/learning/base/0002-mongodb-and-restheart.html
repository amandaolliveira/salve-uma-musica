Lesson 2: How MongoDB and RESTHeart store your songs

Win: create the musica collection, save one song document, read it back, and explain why PUT and PATCH behave differently. Needs lesson 1 done (containers running).

1. Documents and collections

MongoDB stores documents: JSON-like objects with fields. A collection is a group of documents, roughly what a table is in SQL, except documents in one collection may have different fields. (MongoDB docs: Documents) The game uses two collections: musica (songs) and artista (artists). One song is one document (the full model is in docs/estrutura_banco.md):

{
  "_id": 518458172,                   // unique key of the document (Deezer's track id)
  "titulo": "Sweet Child O' Mine",
  "duracao": 355,                     // number
  "artista": { "id_artista": 663, "nome_artista": "Guns N' Roses" },   // embedded object
  "genero": "Rock",
  "vitorias": 0
}

_id is the unique key. Two documents in one collection cannot share it. That is why the project uses Deezer's track ID as _id: the same song can never be saved twice.

2. What RESTHeart does

MongoDB speaks its own protocol, not HTTP. RESTHeart sits in front of it and translates HTTP requests into MongoDB operations. (RESTHeart docs: tutorial) The URL path is the collection, and the method is the operation:

PUT    /musica          create the collection
POST   /musica          insert a document   (201, id in the Location header)
GET    /musica          list documents
GET    /musica/123      one document        (200, or 404 if missing)
PUT    /musica/123      replace a document  (200)
PATCH  /musica/123      change some fields  (200)
DELETE /musica/123      remove a document   (204)

3. The four traps (tested on this project's RESTHeart)

  • POST with an _id that exists gives 409 and changes nothing. You cannot "save again" with POST. The import uses this on purpose: a 409 means "already in the database".
  • PUT replaces the whole document. Send only {"titulo": "x"} and every other field, including vitorias, is wiped. That is why the edit form in app.js sends the full document.
  • PATCH merges. It changes only the fields you send. {"$inc": {"vitorias": 1}} adds 1 to a number, which is how the game records a win.
  • The type of _id matters. The text "1" and the number 1 are different keys. A URL like /musica/1 looks for the text, so a document stored with the number answers 404 there, even though it shows in the list. This project keeps the number (as in docs/estrutura_banco.md), so every request by id for an imported song needs ?id_type=NUMBER, for example /musica/1?id_type=NUMBER. In app.js this is done in a single function, urlDocumento, so it cannot be forgotten. Songs added by hand have no Deezer id; MongoDB gives them an ObjectId, which needs no extra parameter.

4. Try it

Start the containers (docker compose up -d). In Windows PowerShell use curl.exe (plain curl is a different PowerShell command). Create a file doc.json in your scratch folder with a test song:

{ "_id": 1, "titulo": "Teste", "duracao": 100, "vitorias": 0 }
curl.exe -i -u admin:secret -X PUT http://localhost:8080/musica
curl.exe -i -u admin:secret -X POST -H "Content-Type: application/json" -d "@doc.json" http://localhost:8080/musica
curl.exe -i -u admin:secret http://localhost:8080/musica/1
curl.exe -u admin:secret "http://localhost:8080/musica/1?id_type=NUMBER"

Expect 201 on the first (200 if the app already created the collection) and 201 on the POST. The third answers 404 and the fourth returns your document: that is trap 4. Run the POST a second time and watch the 409. Then delete the test data so it does not pollute your ranking:

curl.exe -i -u admin:secret -X DELETE "http://localhost:8080/musica/1?id_type=NUMBER"

Confused by a status code? Copy the full output before asking for help. The same requests become point-and-click in Postman next lesson.

Aula 2: Como o MongoDB e o RESTHeart guardam suas músicas

Objetivo: criar a coleção musica, salvar um documento de música, lê-lo de volta e explicar por que PUT e PATCH se comportam de forma diferente. Precisa da aula 1 concluída (contêineres rodando).

1. Documentos e coleções

O MongoDB guarda documentos: objetos parecidos com JSON, com campos. Uma coleção é um grupo de documentos, mais ou menos o que uma tabela é no SQL, só que os documentos de uma mesma coleção podem ter campos diferentes. (Documentação do MongoDB: Documents, em inglês) O jogo usa duas coleções: musica (músicas) e artista (artistas). Uma música é um documento (o modelo completo está em docs/estrutura_banco.md):

{
  "_id": 518458172,                   // chave única do documento (id da faixa no Deezer)
  "titulo": "Sweet Child O' Mine",
  "duracao": 355,                     // número
  "artista": { "id_artista": 663, "nome_artista": "Guns N' Roses" },   // objeto embutido
  "genero": "Rock",
  "vitorias": 0
}

O _id é a chave única. Dois documentos da mesma coleção não podem ter o mesmo. Por isso o projeto usa o ID da faixa no Deezer como _id: a mesma música nunca é salva duas vezes.

2. O que o RESTHeart faz

O MongoDB fala o próprio protocolo, não HTTP. O RESTHeart fica na frente dele e traduz requisições HTTP em operações do MongoDB. (Documentação do RESTHeart: tutorial, em inglês) O caminho da URL é a coleção e o método é a operação:

PUT    /musica          cria a coleção
POST   /musica          insere um documento   (201, id no cabeçalho Location)
GET    /musica          lista os documentos
GET    /musica/123      um documento          (200, ou 404 se não existir)
PUT    /musica/123      substitui um documento (200)
PATCH  /musica/123      altera alguns campos  (200)
DELETE /musica/123      remove um documento   (204)

3. As quatro armadilhas (testadas no RESTHeart deste projeto)

  • POST com um _id que já existe retorna 409 e não muda nada. Não dá para "salvar de novo" com POST. A importação usa isso de propósito: um 409 significa "já está no banco".
  • PUT substitui o documento inteiro. Se você enviar só {"titulo": "x"}, todos os outros campos, inclusive vitorias, são apagados. Por isso o formulário de edição do app.js envia o documento completo.
  • PATCH mescla. Ele altera apenas os campos enviados. {"$inc": {"vitorias": 1}} soma 1 a um número, e é assim que o jogo registra uma vitória.
  • O tipo do _id importa. O texto "1" e o número 1 são chaves diferentes. Uma URL como /musica/1 procura o texto, então um documento guardado com o número responde 404 ali, mesmo aparecendo na lista. Este projeto mantém o número (como no docs/estrutura_banco.md), então toda requisição por id de uma música importada precisa de ?id_type=NUMBER, por exemplo /musica/1?id_type=NUMBER. No app.js isso fica em uma única função, urlDocumento, para não ser esquecido. Músicas adicionadas à mão não têm id do Deezer; o MongoDB dá a elas um ObjectId, que não precisa de parâmetro extra.

4. Experimente

Suba os contêineres (docker compose up -d). No PowerShell do Windows use curl.exe (o curl sem o .exe é outro comando do PowerShell). Crie um arquivo doc.json na sua pasta de testes com uma música de teste:

{ "_id": 1, "titulo": "Teste", "duracao": 100, "vitorias": 0 }
curl.exe -i -u admin:secret -X PUT http://localhost:8080/musica
curl.exe -i -u admin:secret -X POST -H "Content-Type: application/json" -d "@doc.json" http://localhost:8080/musica
curl.exe -i -u admin:secret http://localhost:8080/musica/1
curl.exe -u admin:secret "http://localhost:8080/musica/1?id_type=NUMBER"

Espere 201 na primeira (200 se o app já criou a coleção) e 201 no POST. A terceira responde 404 e a quarta devolve o seu documento: é a armadilha 4. Rode o POST uma segunda vez e veja o 409. Depois apague os dados de teste para não sujar o seu ranking:

curl.exe -i -u admin:secret -X DELETE "http://localhost:8080/musica/1?id_type=NUMBER"

Confuso com algum código de status? Copie a saída completa antes de pedir ajuda. As mesmas requisições viram cliques no Postman na próxima aula.
