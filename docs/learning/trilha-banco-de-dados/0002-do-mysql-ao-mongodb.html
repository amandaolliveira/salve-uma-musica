2. Queries side by side

MySQL                                         MongoDB (shell / Compass)
SELECT * FROM musica WHERE genero = 'Rock';   db.musica.find({ genero: "Rock" })
SELECT COUNT(*) FROM musica;                  db.musica.countDocuments()
SELECT * FROM musica                          db.musica.find().sort({ vitorias: -1 }).limit(10)
  ORDER BY vitorias DESC LIMIT 10;
UPDATE musica SET vitorias = vitorias + 1     db.musica.updateOne({ _id: 1 }, { $inc: { vitorias: 1 } })
  WHERE id = 1;
ALTER TABLE musica ADD atualizado_em ...;     (nothing: just write the new field)

Through RESTHeart (HTTP) the first one is GET /musica?filter={"genero":"Rock"}, and the UPDATE is PATCH /musica/1?id_type=NUMBER with {"$inc": {"vitorias": 1}}. That PATCH is exactly what the game sends when a song wins.

3. The same data, modelled both ways

In MySQL you would have two tables and a JOIN every time you list songs:

CREATE TABLE artista (id INT PRIMARY KEY, nome VARCHAR(200), url_foto VARCHAR(500));
CREATE TABLE musica  (id BIGINT PRIMARY KEY, titulo VARCHAR(200), duracao INT,
                      id_artista INT, FOREIGN KEY (id_artista) REFERENCES artista(id));

SELECT m.titulo, a.nome FROM musica m JOIN artista a ON a.id = m.id_artista;

In this project the song document already carries what the screen needs:

{
  "_id": 518458172,
  "titulo": "Sweet Child O' Mine",
  "artista": { "id_artista": 663, "nome_artista": "Guns N' Roses" },   // embedded
  "duracao": 355,
  "genero": "Rock",
  "vitorias": 0,
  "criado_em": "2026-11-05T22:40:00.000Z"
}

Listing songs is one read, no JOIN. The artista collection still exists, with the artist's photo, and id_artista points to it: that part is referenced.

4. Embed or reference?

(MongoDB docs: embedded data vs references) A rule of thumb:

  • Embed what is always read together with the parent. The artist name shows in every list and every round of the game.
  • Reference what is shared by many documents, rarely needed, or changes on its own. The photo is used by no screen today, and one artist has many songs.
  • The price of embedding: the name is copied into every song of that artist. If the artist changed name, every song would need an update. It is rare, so the copy is worth it.

5. No fixed schema

Documents in the same collection may differ. In this project:

  • A song added by hand has artista.id_artista: null and an _id generated by MongoDB (an ObjectId), not a number.
  • atualizado_em only exists after a song is edited (PUT) or wins / is reset (PATCH).

Without a schema, nothing in the database forces duracao to be a number. That check happens in the app, in the function validar of frontend/app.js.

3. Os mesmos dados, modelados dos dois jeitos

No MySQL você teria duas tabelas e um JOIN toda vez que listasse as músicas:

CREATE TABLE artista (id INT PRIMARY KEY, nome VARCHAR(200), url_foto VARCHAR(500));
CREATE TABLE musica  (id BIGINT PRIMARY KEY, titulo VARCHAR(200), duracao INT,
                      id_artista INT, FOREIGN KEY (id_artista) REFERENCES artista(id));

SELECT m.titulo, a.nome FROM musica m JOIN artista a ON a.id = m.id_artista;

Neste projeto, o documento da música já carrega o que a tela precisa:

{
  "_id": 518458172,
  "titulo": "Sweet Child O' Mine",
  "artista": { "id_artista": 663, "nome_artista": "Guns N' Roses" },   // embutido
  "duracao": 355,
  "genero": "Rock",
  "vitorias": 0,
  "criado_em": "2026-11-05T22:40:00.000Z"
}

Listar as músicas é uma leitura só, sem JOIN. A coleção artista continua existindo, com a foto do artista, e o id_artista aponta para ela: essa parte é referenciada.

4. Embutir ou referenciar?

(Documentação do MongoDB: dados embutidos x referências, em inglês) Uma regra prática:

  • Embuta o que é sempre lido junto com o documento pai. O nome do artista aparece em toda listagem e em todo round do jogo.
  • Referencie o que é compartilhado por muitos documentos, quase nunca usado, ou muda por conta própria. A foto não é usada por nenhuma tela hoje, e um artista tem várias músicas.
  • O preço de embutir: o nome é copiado em toda música daquele artista. Se o artista mudasse de nome, todas as músicas precisariam ser atualizadas. É raro, então a cópia vale a pena.

5. Sem esquema fixo

Documentos da mesma coleção podem ser diferentes. Neste projeto:

  • Uma música adicionada à mão tem artista.id_artista: null e um _id gerado pelo MongoDB (um ObjectId), não um número.
  • O atualizado_em só existe depois que a música é editada (PUT) ou vence / é zerada (PATCH).

Sem esquema, nada no banco obriga o duracao a ser um número. Essa conferência acontece no app, na função validar do frontend/app.js.
