2. What happens when the page opens

iniciar()
  ligarEventos()            buttons and forms start working
  garantirColecoes()        GET /musica?pagesize=1  -> 404? then PUT /musica (201)
                            same for /artista
  recarregar()              GET /musica?pagesize=1000, then list + dashboard
  carregarGenerosDeezer()   GET /deezer/genre (through the nginx proxy)

That is why the professor only needs docker compose up -d: the collections are created by the page itself.

3. Where each HTTP method happens

MethodFunctionTriggered by
GETdeezerGenre list and import (Deezer, through the proxy)
GETlistarMusicas / buscarMusicaEvery reload / the Edit button (search by id)
POSTinserirImport (each song and artist) and the "Adicionar" form
PUTsubstituirMusicaSaving the edit form
PATCHalterarMusicaEnd of a game ($inc on vitorias) and "Zerar vitórias"
DELETEexcluirMusicaThe Delete button, after confirm()

4. Four details you should be able to explain

  • urlDocumento: imported songs have a number as _id, so their URL gets ?id_type=NUMBER. Manual songs have an ObjectId ({ "$oid": "..." }), so the URL uses that text.
  • inserir accepts 409: 409 means "this _id already exists". On import that is expected, so it counts as "already in the database" instead of an error.
  • The PUT keeps fields the form does not show: in aoEnviarFormulario, const { _id, _etag, ...resto } = edicao takes the document loaded by the GET, removes _id (it goes in the URL) and _etag (RESTHeart's), and keeps the rest (vitorias, criado_em...). Without that, the PUT would wipe them.
  • executar + recarregar: every change runs inside executar (shows loading, then success or the error with the HTTP status) and ends with recarregar(). That is the requirement "indicators update after every POST, PUT, PATCH or DELETE".
Optional: how the game picks the winner

jogo.faseAtual holds the songs still in the game. Each round shows positions indice and indice + 1; the chosen one goes to jogo.proximaFase. When the phase ends, proximaFase becomes faseAtual. When only one is left, finalizarJogo sends the PATCH.

5. Try it

With docker compose up -d running, open http://localhost:3000, press F12 and open the Network tab. Type 8080 in its filter box. Then:

  1. Click Editar on a song: you see a GET for that id.
  2. Change the title and save: a PUT, then a GET of the list (that is recarregar).
  3. Click Zerar vitórias: a PATCH.
  4. Play an 8-song game: no request during the rounds, one PATCH at the end.

The Status column shows the code of each request. Compare it with the table in section 3.

3. Onde acontece cada método HTTP

MétodoFunçãoDisparado por

4. Quatro detalhes que você precisa saber explicar

  • urlDocumento: músicas importadas têm um número como _id, então a URL delas ganha ?id_type=NUMBER. Músicas manuais têm um ObjectId ({ "$oid": "..." }), então a URL usa esse texto.
  • O inserir aceita 409: 409 significa "esse _id já existe". Na importação isso é esperado, então conta como "já estava no banco" em vez de erro.
  • O PUT mantém os campos que o formulário não mostra: no aoEnviarFormulario, const { _id, _etag, ...resto } = edicao pega o documento carregado pelo GET, tira o _id (vai na URL) e o _etag (do RESTHeart), e mantém o resto (vitorias, criado_em...). Sem isso, o PUT apagaria esses campos.
  • executar + recarregar: toda alteração roda dentro do executar (mostra carregando, depois sucesso ou o erro com o status HTTP) e termina com recarregar(). É o requisito "os indicadores se atualizam depois de cada POST, PUT, PATCH ou DELETE".
Opcional: como o jogo escolhe a vencedora

jogo.faseAtual guarda as músicas que ainda estão no jogo. Cada round mostra as posições indice e indice + 1; a escolhida vai para jogo.proximaFase. Quando a fase acaba, proximaFase vira faseAtual. Quando sobra uma, o finalizarJogo envia o PATCH.
